# 제품 요구사항 정의서: `doop` v0.2

* **문서 상태:** 범위 승인
* **기준 문서:** `docs/prd/init-prd.md` 2.0
* **범위:** v0.1에 16진수 변환 두 개를 추가하는 승인된 요구사항
* **제품 UI 언어:** 영어
* **문서 언어:** 한국어
* **후속 승인 설계:** `docs/superpowers/specs/2026-07-31-doop-tui-workbench-design.md`

---

# 1. 목적과 범위

v0.2는 기존 여섯 변환에 사람이 읽고 복사하기 쉬운 16진수 변환을 더한다. CLI와 TUI는 계속 하나의 정적 변환 레지스트리와 공용 파이프라인을 사용하며, v0.2의 등록 변환 수는 정확히 8개다.

v0.1의 입력원, CLI 출력 원자성, 종료 코드, 자원 한도, TUI 비파괴 작업판, 터미널 출력 안전성 및 공통 오류 표시 정책은 `docs/prd/init-prd.md`를 따른다.

## 1.1 후속 TUI 설계와의 관계

2026-07-31에 바이트 Pipeline TUI 설계가 후속 승인되었다. 기능 구현과 단위 시험에는 CLI `StrictText`와 TUI `AllowBinary` 정책 분리가 반영되었으며, macOS·Linux 실제 TUI와 클립보드 통합 검증은 수행 대기 상태다. 해당 검증까지 완료되면 다음 v0.2 규약은 CLI에만 남고 TUI에는 새 설계가 우선한다.

* 원시 이진 결과를 성공 결과로 제공하지 않음
* `hex-decode` 결과가 유효한 UTF-8일 때만 성공함
* 비 UTF-8 디코딩 결과를 `InvalidUtf8Output`으로 처리함

전환 완료 전 규약의 기준은 계속 이 PRD다. 변환 ID, 입력 문법, 오류 오프셋, 출력 한도와 CLI 규약은 후속 설계에서도 변경하지 않는다.

## 1.2 포함 기능

추가하는 공개 변환 식별자는 다음 두 개이며, 공개 후 변경하지 않는다.

1. `hex-encode`
2. `hex-decode`

v0.2의 공개 변환 식별자 집합은 다음 여덟 개다. 각 식별자는 한 번만 등록하며 `tui`와 충돌하지 않는다.

* `base64-encode`, `base64-decode`
* `url-encode`, `url-decode`
* `format-json`, `minify-json`
* `hex-encode`, `hex-decode`

`doop --list`, 변환별 도움말, CLI 명령 해석, TUI 변환 선택, 파이프라인 식별자 조회는 하나의 공용 레지스트리를 공유한다. 목록 표시 순서는 v0.2의 공개 호환성 규약이 아니다.

## 1.3 비목표와 보류 항목

다음은 v0.2에 구현하지 않는다.

* 대문자 16진수 인코딩
* `0x` 접두사, 콜론, 쉼표 또는 임의 구분자가 있는 입력
* 원시 이진 결과를 CLI 성공 결과로 제공하는 기능
* 바이트 그룹화, 줄 감싸기, 줄바꿈 추가, 접두사 추가
* 변환별 옵션, 새 16진수 의존성, 플러그인 또는 별도 변환 크레이트

이 항목은 실제 사용 요구가 확인될 때 별도 버전에서 검토한다.

# 2. 변환 요구사항

## 2.1 `hex-encode`

표시 이름은 `Hex Encode`다.

* 임의 바이트 입력을 허용한다.
* CLI는 표준 입력 또는 `--input` 파일로 받은 임의 바이트를 지원한다. TUI Input은 v0.1의 UTF-8 문자열 범위를 유지하므로 임의의 비 UTF-8 바이트를 직접 입력하지 않는다.
* 각 입력 바이트를 정확히 두 개의 소문자 ASCII 16진수 문자로 출력한다.
* 출력에는 `0x` 접두사, 구분자, 그룹화, 공백, 줄바꿈을 추가하지 않는다.
* 빈 입력은 빈 출력으로 변환한다.
* 결과 길이는 입력 길이의 두 배다. 계산 오버플로와 단계 출력 한도를 할당 전에 검사한다.

예: `b"\x00\xffA"`는 `00ff41`이 된다.

## 2.2 `hex-decode`

표시 이름은 `Hex Decode`다.

* 입력은 유효한 UTF-8이어야 한다. 이 조건은 기존 파이프라인의 텍스트 입력 검증으로 적용한다.
* ASCII space (`0x20`), tab (`0x09`), CR (`0x0d`), LF (`0x0a`)만 무시한다.
* `0`–`9`, `a`–`f`, `A`–`F`만 16진수 숫자로 허용한다.
* 그 밖의 모든 바이트는 오류다. 여기에는 `0x`의 `x`, 콜론, 쉼표, 비 ASCII 공백이 포함된다.
* 공백을 제거한 16진수 숫자 수가 홀수이면 오류다.
* CLI `StrictText`는 성공한 바이트열이 유효한 UTF-8일 때만 성공한다. TUI `AllowBinary`는 원시 바이트 성공 결과를 보존해 Hex View와 소문자 Hex 복사를 제공한다.
* 두 정책 모두 손실 치환이나 부분 성공 결과를 제공하지 않는다.

예: `48 65\n6C6c6F`와 `48656c6C6f`는 모두 `hello`가 된다.

# 3. 오류와 한도

## 3.1 입력 위치와 형식 오류

16진수 입력의 바이트 오프셋은 원본 입력 바이트열에서 0부터 센다. 무시하는 ASCII 공백도 오프셋 계산에는 포함한다.

* 허용되지 않는 문자는 `invalid hex character at byte {position}`으로 보고한다. `{position}`은 해당 바이트의 원본 오프셋이다.
* `0x`는 `x`가 원본 오프셋 1에 있으므로 `invalid hex character at byte 1`이다. 접두사 오류나 숫자 수 오류로 재해석하지 않는다.
* 콜론과 쉼표도 각 문자의 원본 오프셋에서 같은 오류로 보고한다.
* 유효한 UTF-8의 비 ASCII 공백은 첫 UTF-8 바이트의 원본 오프셋에서 같은 오류로 보고한다. ASCII 네 종류 이외의 공백은 무시하지 않는다.
* 유효 문자와 허용 공백만 남은 뒤 숫자 수가 홀수이면 `hex input has an odd number of digits: {digits}`로 보고한다. 이 경우 잘못된 문자 위치는 없으며 `{digits}`는 공백을 제외한 숫자 수다.

16진수 형식 오류와 단계 출력 한도 초과는 기존 변환 오류로 처리하여 CLI는 코드 `4`, 표준 출력은 비운다. 파이프라인은 기존처럼 1부터 시작하는 단계 번호와 변환 식별자를 오류에 포함한다.

## 3.2 UTF-8 결과와 출력 한도

CLI에서 `hex-decode` 결과가 UTF-8이 아니면 기존 `InvalidUtf8Output` 정책을 그대로 사용한다. TUI에서는 같은 바이트열을 성공 Artifact로 유지하고 Smart View가 Hex를 선택한다.

* 오류 자료에는 처음 최대 64바이트의 소문자 16진수 미리보기와 전체 바이트 수를 보존한다.
* 기존 표준 오류 표시는 64바이트를 넘으면 생략 사실과 전체 바이트 수를 함께 표시한다.
* 입력 원문, 전체 디코딩 결과, 손실 치환 문자열은 표시하지 않는다.

디코딩은 유효 숫자 수를 먼저 세고, 짝수성 및 `유효 숫자 수 / 2`의 단계 출력 한도를 검사한 뒤에만 결과 버퍼를 할당한다. 인코딩은 `입력 길이 * 2`를 검사된 산술로 계산해 한도 확인 뒤에만 할당한다. 적용 한도는 기존과 같이 CLI 단계당 256 MiB, TUI 단계당 64 MiB다.

# 4. 인수 기준

* v0.2 레지스트리는 위 여덟 공개 식별자만 한 번씩 포함하고 `tui`와 충돌하지 않는다. 목록 표시 순서는 공개 호환성 규약이 아니다.
* `hex-encode`는 임의 바이트를 소문자 16진수로만 바꾸고 부가 문자를 쓰지 않는다.
* `hex-decode`는 네 종류의 ASCII 공백 및 대소문자 16진수만 허용한다.
* `0x`의 `x`, 콜론, 쉼표, 비 ASCII 공백은 원본 바이트 오프셋의 `invalid hex character` 오류가 된다.
* 홀수 숫자 수는 공백을 제외한 정확한 숫자 수를 포함한 `odd number of digits` 오류가 된다.
* 비 UTF-8 디코딩 결과는 CLI에서 기존 64바이트 16진수 미리보기와 전체 길이 정책으로 실패하고, TUI에서는 Hex로 확인·복사할 수 있다.
* 두 변환은 기존 입력·출력 한도와 검사된 할당을 따르며 새 16진수 의존성을 추가하지 않는다.
* CLI와 TUI는 같은 레지스트리와 실행 함수를 사용한다. 모든 활성 단계의 출력이 유효한 UTF-8이면 최종 결과가 같다. 중간 단계에서 비 UTF-8이 나오면 이후 바이트 허용 단계가 최종 텍스트를 만들더라도 CLI `StrictText`는 해당 중간 단계에서 `InvalidUtf8Output`으로 실패하고, TUI `AllowBinary`만 실행을 계속한다.
